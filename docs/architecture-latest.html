The chart runs in a tab, and the agent knocks on a door.

A Hermes Desktop plugin puts one row in the sidebar and one pane beside the chat. That pane is an iframe onto a local Python server (127.0.0.1:8787) which serves the real LuxAlgo Vela console. The agent cannot reach into the tab, so both sides meet in the middle: a push channel plus a file bridge. Pine is computed by our own vendored PineTS in a worker, and only what Vela can honestly draw is drawn.

Push channel — SSE

The page holds one long-lived request open; the backend pushes a command the moment it is queued. This is what turned a 1–2 s poll into tens of milliseconds.

File bridge — durable

Commands, results and state are still written to disk, so a view that is not streaming works on the old schedule.

Heartbeat & execute-once claim

State every 4 s; commands polled every 2 s (15 s when SSE is live). Each page carries a random viewer id so two consoles can never both run one command.

claimed once per VIEWERpushed commands never re-run on poll

Action whitelist from the page

The page publishes what it can actually execute in every heartbeat; the server validates against that, not a constant. The two drifted once — an action passed the server and came back “unknown action” with HTTP 200.

Build stamp — stale frames become visible

An occluded renderer keeps its last painted frame, so a pane can sit on hours-old code. The heartbeat carries the build the frame loaded, so “this view runs build X, the server serves Y” is readable from the agent’s side instead of looking like a broken feature.

Read this before anything else

Vela’s own Pine engine is wired and registered, and on a live chart it frequently never executes a script — measured silences of 90 s · 112 s · 40 s · 75 s with promises that never settle. So the console runs PineTS itself, over the chart’s own bars, and paints the result onto the chart. That is the whole reason this lane exists.

Seven stages, one path

Source → pre-flight → worker → engine → split → paint → report. See section 03.

02

One command, end to end

The agent never touches the chart. It writes a command into the middle, the page picks it up, executes it, and posts the result back — so the caller gets an answer in the same round trip that a poll would have paid 1–2 s of pure overhead for.

You ask, in chat — Telegram or the desk chat. the same Hermes session either way; the composer is Hermes’s own
The agent picks one of 39 tools by name. chart_state · chart_add_indicator · chart_draw · chart_apply_pine · chart_shot …
MCP posts to the console. POST /api/chart/command → 127.0.0.1:8787
The console writes it to disk and publishes it on the SSE queue. durable path first — a view that is not streaming still gets it, just on the old 2 s schedule
The page pops it and claims it once. per-viewer claim; a pushed command is remembered so the next poll cannot re-run it
It executes against the live Vela chart. the server checks the action against the list this page published in its heartbeat
The page posts the result back. POST /api/chart/result — which releases the caller waiting on the same round trip
You get an answer that reflects the chart after the call — and a picture only if it was asked for. a request echoed back is not a painted pane

03

The Pine lane — what happens to a Library script

Three doors ask for Pine: the MCP tools behind chat, the Library card’s Run PineTS, and the console’s own script editor. They all now run one pipeline, in seven stages.

1 · SourceLuxAlgo MCP · editor · agent
Pine arrives as text. Nothing from the Library is copied into this repo — it is fetched at runtime, drawn, and attributed.
2 · Pre-flightpinets-runner.js
Comments are stripped first, so a construct merely named in prose never blocks a file that does not use it. What remains on the refusal list is one thing: import (LuxAlgo’s own libraries). while and for … in were refused here for months and they both run — that stale guard sat in front of 450 of 806 indicators.
3 · Workerpinets-worker.js · own thread
The run leaves the page’s only JS thread. A 20-second run used to tick a 250 ms interval zero times, so no timer could rescue it and every queued command waited behind it — the pane read as dead while it was working. The slowest script measured 301 s. Only worker.terminate() can interrupt that.
4 · Enginepinets 0.10.0 · our fork
The chart’s own bars go in — and they now carry getSymbolInfo, which is what fills syminfo. 146 of 203 crashes were scripts reading it, and that single fix moved coverage from 74 % to 91 %.
5 · Splitunified.js
One run, two outputs. A drawing declared with xloc.bar_time carries milliseconds, not bar indices — those rows are translated onto the bars’ own timeline instead of being dropped, which is why an entire indicator’s shaded zones stopped vanishing.
6 · Paintoverlay.js · pinets-layer.js
Every plot series is drawn by seriesPaths() as a path on the overlay canvas (z 25), alongside boxes, lines, labels and tables (z 26). Additionally, and only if the live catalog confirms an exact type, one series may become a Vela native — the mapper stands aside when a script declares its own drawings, and a script’s own title is consulted before a heuristic, so a dashboard that merely uses ATR is no longer painted as stacked ATR panes.
7 · Reportsummarize()
Every door prints the same line, and it reports what was actually drawn — never trust what the engine stored. A drawing that cannot be placed is dropped, and the report says so.
Rail A — the overlay paints first, and paints most

Boxes, lines, labels and tables, plus every plot series as a path — seriesPaths() turns each plot into a polyline and the canvas strokes it. Not LuxAlgo lookalikes: the script’s own colours and geometry, on our own canvas, above the chart and below the console’s surfaces.

Rail B — and one series may additionally become a Vela native

Only where the catalog has an exact match, and only one native at a time. When there is no match, the plot is still drawn — it just stays a path on the overlay instead of becoming an indicator Vela owns. What is never done is drawing something plausible in its place.

Boundaries — the parts that are not a bug

Hard stops — the design, not a defect

  • One indicator per chart. Replace, never stack.
  • No headless mode. Zero attached views means nothing can be driven — the chart is the renderer, and it must be on screen.
  • Never open a second browser view while the pane is live. A second view attaches to the backend and a command can be routed to the tab that has no bars.
  • PineTS refuses import — and nothing else. while and for … in run; a guard that says otherwise is a claim about the engine and it decays.
  • Binance only. Any other symbol is refused in ~6 s instead of hanging.
  • No claim without a picture. A tool answer is not proof a pane changed.

What it is not — said plainly

  • Not affiliated with LuxAlgo. Never their logo or wordmark; Vela loads from their CDN and their Library Pine is fetched at runtime, never committed (CC BY-NC-SA 4.0).
  • Not hosted. No accounts, no telemetry, no cloud. Every command is localhost except the Library lookups you explicitly ask for.
  • Not a TradingView clone. “Runs” means the engine returned plots; it does not mean the numbers match.
  • Not a bundled engine anymore. The pinets fork is AGPL-3.0-only and redistributed here — fine to give away, a blocker only if this is ever sold.
  • Not a vectorbt install. The backtest tier is installed into its own venv by hand, Apache-2.0 with Commons Clause, and is not running unless you start it.
